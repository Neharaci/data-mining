Q2(d) RELATIONAL HOME AND ACCESS PATH
=====================================

RELATIONAL DESIGN
-----------------
notice_minhash:
- notice_id PRIMARY KEY
- signature BYTEA

lsh_buckets:
- band
- bucket_hash
- notice_id
- PRIMARY KEY (band, bucket_hash, notice_id)

INDEXES
-------
idx_lsh_bucket ON lsh_buckets(band, bucket_hash)
idx_lsh_notice ON lsh_buckets(notice_id)

The retrieval structure is persisted in PostgreSQL so that the
candidate-generation structure survives pipeline reruns and can be
queried directly by the analytical system.

COMPARISON
----------
The indexed query took 0.031 ms.
The forced sequential scan took 1.593 ms.

The sequential scan examined the full bucket table and removed
52,606 non-matching rows, while the index scan used the
(band, bucket_hash) access path to locate the matching bucket.

The measured execution time was approximately 51.4 times higher
for the forced sequential scan in this test.

ALTERNATIVE REJECTED
--------------------
A sequential scan was rejected for routine candidate retrieval
because retrieval repeatedly filters by band and bucket_hash.
The indexed access path avoids scanning unrelated bucket rows.

NOTE
----
The indexed test demonstrates the relational access-path behavior
on the trusted labelled subset used for the retrieval-quality
experiment.
